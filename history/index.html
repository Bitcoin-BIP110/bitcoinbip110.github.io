Overview

What is Bitcoin BIP110?

Bitcoin BIP110 originated from the effort to enforce BIP 110, a proposal for temporary consensus restrictions on certain uses of data in Bitcoin transactions.

The proposal's mandatory-signaling period began on 8 August 2026. At block height 961,632, nodes enforcing BIP 110 rejected a block that did not contain the required signal, while nodes not enforcing the proposal accepted it. The enforcing nodes instead accepted a competing signaling block at the same height. This caused the BIP 110 enforcement branch to split from the Bitcoin BTC mainnet from height 961,632 onward.

The signaling block became the first block of the BIP 110 enforcement branch. Although the branch continued to use SHA-256d proof-of-work and the inherited mining difficulty, it attracted only a small fraction of the network hash power. This resulted in long intervals between blocks and prevented the branch from operating at the normal pace.

Development subsequently began within the Bitcoin Knots on a hard fork that would replace SHA-256d with BLAKE2b and allow the enforcement branch to continue operating.

Bitcoin BIP110 is this independent network intended to continue the historical BIP 110 enforcement branch by transitioning its proof-of-work system to BLAKE2b.

Chapter 1

BIP 110 Proposal

BIP 110 was written by Dathon Ohm and credited Luke Dashjr with the original draft and advice. Its initial draft was recorded on 24 October 2025, it was assigned BIP number 110 on 3 December 2025, and it advanced to Complete status on 25 June 2026.[1]

The proposal described arbitrary-data storage as a burden on node operators and as competition for block space that could otherwise be used for payments. It proposed seven temporary consensus restrictions intended to remain active for 52,416 blocks, approximately one year, while longer-term approaches were considered.

Proposed consensus rules

If the deployment reached its ACTIVE state, blocks would be checked against seven additional rules:

  1. Newly created output scripts longer than 34 bytes would be invalid, except that an output beginning with OP_RETURN could contain up to 83 bytes.
  2. Individual OP_PUSHDATA* payloads and script-argument witness items longer than 256 bytes would be invalid, with an exemption for BIP 16 redeem scripts.
  3. Spending an undefined witness version or undefined Tapleaf version would be invalid, although creating an output using an undefined witness version would remain valid.
  4. Taproot spends containing an annex would be invalid.
  5. Taproot control blocks longer than 257 bytes would be invalid.
  6. Tapscripts containing an OP_SUCCESS* opcode would be invalid, including when the opcode appeared in an unexecuted branch.
  7. Tapscripts executing OP_IF or OP_NOTIF would be invalid regardless of the condition's result.

The proposal distinguished these consensus rules from relay and mining policies, which determine how nodes handle unconfirmed transactions without changing block validity.

UTXO grandfathering

For most input-side checks, an unspent transaction output, or UTXO, created before activation would be exempt. This was intended to preserve the spendability of outputs created under the earlier rules. Outputs created while the deployment was active would remain subject to the new output-size restriction. All BIP 110 restrictions would cease after the temporary deployment expired.[1]

Chapter 2

Signaling and Activation

BIP 110 used a modified form of the BIP 9 version-bits system. Its deployment was named reduced_data and assigned version bit 4. Miners could signal support by setting that bit in the version field of a block.

Parameter BIP 110 value
Start time 1 December 2025, 00:00 UTC
Signaling threshold 1,109 of 2,016 blocks, or 55%
Mandatory-signaling window Heights 961,632 through 963,647
Latest lock-in height 963,648
Latest activation height 965,664
Active duration 52,416 blocks, approximately one year

The 55% threshold was lower than the 95% threshold commonly used by standard BIP 9 deployments. BIP 110 also replaced a time-based failure deadline with a maximum activation height, introduced a period of mandatory signaling, and added an EXPIRED state that would end enforcement after approximately one year.[1]

Mandatory signaling and activation were separate stages. During the mandatory-signaling window, enforcing nodes required bit 4 in every block. The seven reduced-data rules would take effect only after the deployment entered LOCKED_IN and later reached ACTIVE. The enforcement branch did not reach height 963,648 under the original schedule, so the original deployment never locked in and the seven restrictions never became active on that branch.

Chapter 3

Chain Split

Mandatory signaling began on 8 August 2026 at block 961,632. At this block height, AntPool mined a block without version bit 4. Nodes not enforcing BIP 110 accepted the block, while enforcing nodes rejected it because the height was the beginning of the mandatory-signaling window. The enforcing nodes instead accepted a competing bit-4-signaling block mined by Roughnecks through OCEAN DATUM.[3][4]

Bitcoin BTC mainnet and the BIP 110 enforcement branch share the same history through block 961,631. That block, the last common block, has the hash 00000000000000000000807f9dc917442a67910426d79ebb2f8aa2149327ce8a.[2]

After block height 961,632, each group of nodes subsequently treated its own block as the valid block, creating two independent branches.

On 9 August 2026, the official BIP record was changed from Complete to Closed. Its changelog described the reason as a chain split followed by stalled mining.[1]

Chapter 4

Branch History

The enforcement branch initially continued to use SHA-256d, the same proof-of-work algorithm as Bitcoin mainnet. It also inherited a mining difficulty of approximately 127.48 trillion, which had been calibrated for the much larger amount of SHA-256d hash power mining Bitcoin. Only a small fraction of that hash power mined the enforcement branch.

Roughnecks mined the first two branch blocks on 8 August. Later blocks appeared intermittently, with gaps lasting from several hours to more than five days. The observed branch tip on 24 August 2026 was block 961,638.[5]

Bitcoin ordinarily adjusts its mining difficulty every 2,016 blocks. The branch's low block-production rate therefore also delayed its progress toward the next adjustment. This created the operational problem that later motivated development of a different proof-of-work system.

Chapter 5

BLAKE2b Hard Fork

On 15 August 2026, Luke Dashjr opened Bitcoin Knots pull request #359, titled Hardfork: New BLAKE2b proof-of-work algorithm.[6] The proposed implementation accepts SHA-256d blocks before a configured activation height and requires a new BLAKE2b proof-of-work calculation and block-header format beginning at that height.

The proposed hard fork was designed as a continuation of the BIP 110 enforcement branch. It would preserve the branch's earlier Bitcoin history, inherited UTXO set, and SHA-256d branch blocks rather than begin from a new genesis block. Changing proof of work would also allow the implementation to introduce a BLAKE2b-specific starting difficulty and use mining hardware designed for BLAKE2b instead of competing for SHA-256d miners.

Header and mining design

Pull request #359 introduced a 164-byte version-2 block header. The design includes four selectable ASIC profiles, additional nonce space, fields for an opt-in block-withholding defense, future merge-mining support, block height, and a transaction-count commitment. Its stated hardware target is compatibility with several types of Sia-style BLAKE2b mining equipment.[6]

General support for the BLAKE2b function does not by itself establish miner compatibility. Hardware, firmware, pool software, and the new header and job formats must work together for a miner to produce valid blocks.

Testnet releases

Bitcoin Knots published a series of signed release-candidate tags for testing the BLAKE2b transition on testnet4. Each candidate created a separate experimental history when its activation parameters changed.

A public testnet guide documented live validation across RC2's activation height and emphasized that the implementation was unmerged and subject to change.[10] RC3 subsequently changed the activation height again. These testnet parameters did not establish the final composition or activation parameters of a mainnet release.

Related replay-protection work

A change in proof of work does not make ordinary transactions valid on only one chain. A separate Bitcoin Knots proposal, pull request #357, introduced an optional signature mode called SIGHASH_UNIFIED.[11] Signatures that opt in use a different signed message and therefore fail verification on software that does not implement the rule. Transactions signed without the option can remain replayable between compatible histories.

The replay-protection proposal and the BLAKE2b proof-of-work proposal were separate development efforts. Their appearance together in testnet release candidates did not by itself establish that both would appear together under final mainnet rules.

Development status

As of 30 August 2026, pull request #359 remained open and no signed stable Bitcoin BIP110 mainnet release had been published. The BLAKE2b network would become operational on mainnet only after final consensus parameters were published in a release and a valid activation block was mined and independently observed.

Chapter 6

Network Identity

The split at height 961,632 created a block history separate from Bitcoin BTC mainnet. A mainnet BLAKE2b activation would introduce a second consensus boundary through a different proof-of-work algorithm and block-header format. The resulting network would require its own compatible nodes, miners, wallets, explorers, and other infrastructure.

Because the project continues an existing blockchain history, it inherits the Bitcoin ledger and UTXO set through block 961,631 as well as the BIP 110 enforcement-branch blocks that follow. Its asset is therefore a native coin rather than a token issued through a contract.

Bitcoin BIP110 is the pending exchange listed name, and BIP110 is its pending exchange listed ticker.

Historical distinction: Bitcoin BTC mainnet and Bitcoin BIP110 share the history through height 961,631. Their block histories diverge at height 961,632. BLAKE2b is the hard fork of the BIP 110 enforcement branch.
